================================================================================
PART 1 — WHAT THIS PROJECT IS
================================================================================

DEICMS is a Flask web application that manages digital forensic evidence with a
tamper-evident chain of custody, role-based access, and auditability. It is a
university Software Engineering project that must demonstrate three feature
categories in balance:

  A. Data / DB-oriented (CRUD + simple formulae)
  B. Third-party services (libraries, APIs, pre-trained models)
  C. Complex application logic (algorithms you implemented yourself)

Technology: Python 3 + Flask, SQLAlchemy + SQLite, Flask-Login, Flask-WTF
(CSRF), Flask-Limiter, cryptography (Ed25519 + AES-256-GCM), hashlib (SHA-256),
Pillow + python-magic, scikit-learn (Isolation Forest), ReportLab, PyOTP (2FA),
and an LLM assistant via the NVIDIA NIM (Llama 3.1) OpenAI-compatible endpoint.

Core domain entities: Investigator, Case, EvidenceItem, CustodyLog,
AuditRecord, plus CaseAccess (case-level permissions).

The five "complex" (category C) features are:
  1. Chain-of-Custody Graph Integrity Verification (DAG + DFS + per-node checks)
  2. Multi-Factor Evidence Risk Scoring (8 signals, normalisation, interactions)
  3. Custody Chain Reconstruction (heuristic best-first gap filling)
  4. Evidence Lifecycle State Machine (role-gated, precondition-guarded)
  5. AI Investigation Assistant orchestration (intent -> retrieve -> prompt ->
     validate -> hallucination-check)

Security hardening present: password hashing (Werkzeug), account lockout,
rate limiting on auth, CSRF protection, HTTPS with self-signed cert, idle
session timeout, HSTS header, TOTP 2FA, private keys and evidence files
encrypted at rest, append-only audit table (ORM-level update/delete blocks),
magic-byte upload validation, tamper-evident signed ZIP export.

Overall: this is a genuinely ambitious, well-above-average student project. The
breadth is impressive and the category balance is defensible. But several of the
"complex" algorithms do less than the proposal and code comments claim, and a
handful of real bugs mean some features silently do nothing. Details below.

PART 3 — BUGS, WEAK POINTS, INCONSISTENCIES (with recommended solutions)

Ordered roughly by severity. Each item: what it is, why it is bad, and the best

CRITICAL / CORRECTNESS — features that silently do nothing or do the wrong thing
--------------------------------------------------------------------------------

C1. "Soft delete" of evidence does NOTHING (data-integrity bug)
    Where: app/routes/evidence.py:377  ->  evidence.is_deleted = True
    Problem: EvidenceItem has no `is_deleted` column (checked models/evidence.py).
    SQLAlchemy just sets a transient Python attribute that is never persisted,
    and no query anywhere filters on it. So "Delete evidence" writes an audit
    line and then leaves the evidence fully visible everywhere.
    Why bad: the proposal explicitly promises a soft-delete pattern; a delete
    button that does nothing is a correctness and trust failure, and a grader
    will find it in 30 seconds.
    Best fix: add a real `is_deleted = db.Column(db.Boolean, default=False,
    nullable=False)` column (plus an idempotent ALTER in _ensure_schema), set it
    in the route, and add `.filter_by(is_deleted=False)` to every evidence
    listing/lookup (case view, dashboards, risk, custody). Alternatively, if you
    want true immutability of the custody record, replace "delete" with a
    lifecycle state (e.g. an "Withdrawn"/"Archived" evidence flag) rather than a
    delete at all. Justification: matches the proposal's stated soft-delete
    guarantee and preserves the audit trail, which is the whole point of the app.

C2. The highest-weighted risk factor is DEAD (always constant)
    Where: risk_scoring.py:270 and anomaly_detection.py:83 read
    evidence.integrity_status; dashboard.py:117 too.
    Problem: EvidenceItem has no `integrity_status` column. getattr(...) always
    returns None -> "NOT_CHECKED" -> score 0.5 for every item, forever. This
    factor carries the largest weight (0.25). Integrity verification never writes
    an integrity_status back to the evidence row, so running a check has no
    effect on risk.
    Why bad: your flagship risk algorithm's most important signal is a constant.
    Two of the five interaction rules key off integrity_status and can therefore
    almost never fire meaningfully. This undermines the "multi-factor" claim.
    Best fix: add an `integrity_status` column (Enum VERIFIED/NOT_CHECKED/FAILED)
    and update it inside custody.verify_integrity() from report.verdict (Intact
    -> VERIFIED, Broken -> FAILED, Partial -> NOT_CHECKED/FAILED). Then the
    factor and the interaction rules become live. Justification: makes the score
    reflect reality and connects Feature 1 (integrity) to Feature 2 (risk) as the
    proposal describes.

C3. Two risk factors measure the wrong thing (mislabeled queries)
    Where: risk_scoring.py:362-379 (_factor_role_mismatch) and 408-425
    (_factor_duplicates).
    Problem:
      - role_mismatch_count counts AuditRecord rows with result="Warning". But
        the only place that writes evidence-scoped Warning rows is the integrity
        check itself (custody.py:208 uses result='Warning' when verdict != Intact).
        So "role mismatch" actually counts warning-integrity-checks, not role
        mismatches. Nothing ever writes a real ROLE_MISMATCH audit record.
      - duplicate_entry_count counts AuditRecord rows with event_type="Integrity
        Check". So every time you run an integrity check OR a reconstruction
        (both log event_type='Integrity Check'), the "duplicate entries" risk of
        that item goes UP. That is nonsensical: verifying an item makes it look
        riskier.
    Why bad: the numbers are confidently wrong. A grader who traces one factor
    to its source will see the algorithm is not measuring what it says.
    Best fix: define explicit, dedicated audit signals. Either (a) run
    audit_formulas.check_role_mismatches()/check_duplicate_entries() and persist
    their results as dedicated audit rows (e.g. event_type='Integrity Check' with
    a distinct result or a new description tag) and count THOSE, or (b) call the
    formula functions directly inside the factor methods to compute live counts.
    Justification: the formula module already implements the correct logic
    (audit_formulas.py) — wire the risk factors to it instead of to proxy
    queries that happen to be close.

C4. Graph Integrity "per-node hash verification" is not actually per-node
    Where: graph_integrity.py:218-270 (_check_hash).
    Problem: only the Upload (root) node re-hashes the file. For every other
    node the method compares file_hash_at_event to original_hash and then does
    `pass  # Extended hash chain verification goes here in production` — i.e. a
    no-op that always returns True. The proposal and the module docstring both
    claim each node's hash is verified.
    Why bad: the central selling point of Feature 1 — "verify the hash at every
    event, not just the latest" — is not implemented. The completeness score is
    therefore inflated (transfer/access nodes pass their hash check for free).
    Best fix: since files are single-blob (not per-event snapshots), be honest
    about the model: at each node, verify that file_hash_at_event EQUALS the
    file's current verified hash (they should all equal original_hash for an
    untampered linear chain), and flag any node whose recorded hash diverges.
    That is a real per-node check over stored data and is defensible. If you want
    true historical snapshots you would need to store a hash per version — out of
    scope; document that limitation. Justification: either implement a real
    per-node comparison or scope the claim down; right now claim and code
    disagree, which is the worst option.

C5. Custody transfer can crash on the NOT-NULL signature constraint
    Where: custody.py:107-138; model custody_log.py:39 digital_signature
    nullable=False.
    Problem: signature_hex starts as None and is only set if the current user
    has a private key AND signing succeeds. If an investigator has no key (or
    signing throws), the CustodyLog is built with digital_signature=None and the
    commit raises an IntegrityError -> 500 error, losing the transfer.
    Why bad: latent crash. It doesn't fire with seeded users (they all have
    keys) but any admin-created user whose key generation failed, or any signing
    error, breaks transfers.
    Best fix: mirror the upload route, which stores the literal 'UNSIGNED' on
    failure. Set `signature_hex = signature_hex or 'UNSIGNED'` before creating
    the CustodyLog, OR make the column nullable. Prefer the 'UNSIGNED' sentinel
    so the graph verifier can flag unsigned links. Justification: guarantees the
    NOT-NULL invariant holds and keeps unsigned events auditable.

C6. Rejected state transitions are NEVER logged (contradicts the proposal)
    Where: custody.py:283-287 (change_state) and state_machine.py:223-237
    (_log_rejection).
    Problem: _log_rejection adds a Failure audit record to the session, but the
    route calls db.session.rollback() on failure, which discards that audit
    record along with everything else. The proposal states "the rejection is
    written to the audit trail." It isn't (for the manual change-state path).
    Why bad: a documented audit guarantee is broken; failed/denied transition
    attempts vanish, which is exactly the kind of event a forensic audit trail
    exists to capture.
    Best fix: don't roll back the whole session. On failure, commit only the
    rejection audit row (the state machine made no other changes on the failure
    path), or restructure so the rejection audit is written in its own committed
    transaction. Simplest: replace `db.session.rollback()` with
    `db.session.commit()` in the else-branch, since transition_to() does not
    mutate evidence on the failure path. Justification: restores the audit
    guarantee with a one-line change and no risk of persisting a bad state.

C7. Timestamp model default is tz-aware UTC while everything else is naive local
    Where: custody_log.py:27 default=lambda: datetime.now(timezone.utc); the
    rest of the app uses app.utils.now_local() (naive, UTC+2).
    Problem: mixed aware/naive datetimes. If the default ever fires (a CustodyLog
    created without an explicit timestamp), comparing it to naive timestamps in
    the graph verifier / risk scorer raises "can't compare offset-naive and
    offset-aware datetimes", and it is also 2 hours off. All current call sites
    pass an explicit now_local(), so it's latent — but it's a trap.
    Why bad: inconsistent time handling is a classic source of heisenbugs, and
    the timestamp monotonicity check in Feature 1 is sensitive to exactly this.
    Best fix: make the model default `default=lambda: now_local()` like every
    other model, and standardise on one convention (recommend: store UTC, format
    to local only at display time — see A3 below). Justification: one timezone
    convention across the codebase eliminates a whole bug class.

--------------------------------------------------------------------------------
SECURITY
--------------------------------------------------------------------------------

S1. Weak default secrets + app ships in DevelopmentConfig
    Where: config.py:14,72 fallbacks 'dev-secret-key-change-in-production' and
    'dev-encryption-secret-change-in-production'; config=DevelopmentConfig:123.
    Problem: SECRET_KEY signs session cookies; KEY_ENCRYPTION_SECRET derives the
    keys that encrypt BOTH private keys and evidence files at rest. If .env is
    missing, both silently fall back to public, hard-coded values, and the
    ProductionConfig guard (which would crash on missing secrets) never runs
    because the active config is Development.
    Why bad: with the fallback, anyone who knows the (public) default can forge
    sessions and decrypt "encrypted-at-rest" evidence. The encryption becomes
    theatre.
    Best fix: (1) fail fast — raise on startup if either secret is unset, even in
    development, OR generate a random per-install secret persisted outside git.
    (2) Select config from an env var (FLASK_ENV) so production is reachable.
    (3) Document that rotating KEY_ENCRYPTION_SECRET makes existing encrypted
    data unrecoverable (there is no key-rotation path) — see S2. Justification:
    at-rest encryption is only as strong as the secret; a known default defeats
    the entire crypto story you are marketing as a headline feature.

S2. No key rotation / single master secret for all at-rest crypto
    Where: keyderive.py derive_key() from one master secret.
    Problem: every evidence file and every private key is derivable from one
    secret via PBKDF2. Change it and all prior data is unreadable; leak it and
    everything is exposed. No versioning of keys.
    Why bad: operationally fragile; a real forensic system needs key custody and
    rotation.
    Best fix: for the course, document this as an explicit limitation and note
    the production path (per-file data-encryption keys wrapped by a KEK in a
    vault/HSM). If you want to show depth, add a key-version byte to the file
    header so future rotation is possible. Justification: shows you understand
    the threat model even if full rotation is out of scope.

S3. Stored-XSS vector in the AI chat (LLM output rendered as HTML)
    Where: templates/assistant/chat.html:107 bubble.innerHTML = text.replace(...)
    Problem: both user messages and the LLM reply are injected via innerHTML
    after a naive **bold** replace. The reply is attacker-influenceable (a user
    can ask the model to emit HTML/script; the model is a third party). Any
    <img onerror=...> or <script> in the reply executes in the investigator's
    authenticated session.
    Why bad: XSS in an authenticated forensic tool = session/CSRF-token theft,
    action-on-behalf. Undercuts all the other security work.
    Best fix: render as text, not HTML. Use textContent and do the bold/bullet
    formatting with DOM nodes, or sanitise with DOMPurify before insertion, or
    escape HTML then apply a whitelist of formatting. Justification: never trust
    LLM output as markup; this is the one XSS hole in an otherwise CSRF/CSP-aware
    app.

S4. No Content-Security-Policy header
    Where: app/__init__.py:_set_security_headers (only sets HSTS).
    Problem: no CSP, so S3 has nothing to contain it. Inline scripts abound.
    Best fix: add a CSP (at least default-src 'self'; a nonce-based policy if you
    can). Even a report-only CSP demonstrates awareness. Justification:
    defence-in-depth; pairs with S3.

S5. Rate limiting only on login/OTP, in-memory store
    Where: auth.py:26,138 limiter.limit('10/min'); __init__.py limiter memory://
    Problem: expensive endpoints (risk dashboard, integrity verify, reconstruct,
    AI chat, export) are unthrottled; the in-memory store resets on restart and
    is not multi-process safe.
    Why bad: the heavy endpoints (see P1) are the ones worth abusing; a shared
    deployment would not enforce limits consistently.
    Best fix: add modest limits to the compute-heavy routes, and note that a
    production deployment needs a Redis storage backend for the limiter.
    Justification: aligns protection with actual cost.

S6. Evidence files stored under a predictable server path, integrity depends on
    filesystem permissions the app does not enforce
    Where: config UPLOAD_FOLDER = BASE_DIR/uploads; proposal's risk section
    promised a "write-protected directory that only the application process can
    access" and logging of permission changes.
    Problem: neither the write-protection nor the permission-change logging is
    implemented. Files are AES-GCM encrypted (good) but the promised OS-level
    control is absent.
    Best fix: either implement (set restrictive perms on the upload dir at
    startup and detect/log changes) or soften the proposal claim in the report.
    Justification: don't claim controls you didn't build; the AES-GCM tag already
    gives tamper-detection, so lean on that instead.

--------------------------------------------------------------------------------
ALGORITHM / LOGIC QUALITY (category C features under scrutiny)
--------------------------------------------------------------------------------

L1. Chain Reconstruction rests on a shaky gap definition and thin evidence
    Where: chain_reconstruction.py _is_gap():257 and _generate_candidates():273.
    Problems:
      - A "gap" is only detected when to_investigator(prev) != from_investigator(
        next) and both are non-null. But Access events have to=None and Upload
        has from=None, so real discontinuities involving those event types are
        invisible; and a deleted middle transfer often still leaves matching
        from/to and is missed. So the algorithm mostly finds gaps that are, in
        practice, rare in your own data model.
      - Candidates come only from AuditRecord event_type='File Access' inside the
        window; location is always None (access logs have none), so the
        "location consistency" criterion is hard-coded to 0.5 for everyone. That
        is one of four equally-weighted criteria — 25% of the score is a
        constant.
      - The dead ternary at line 170 references log.log_id, which does not exist
        (the column is `id`); hasattr() is always False so it always falls
        through to _is_gap. Works, but it's confusing dead code that looks like a
        bug.
    Why bad: the feature is described as a heuristic search, but two of four
    scoring dimensions are effectively constant (location=0.5 always; temporal is
    real; role is real; behavioural is real), and the gap detector rarely fires.
    It will look impressive in the report and thin under questioning.
    Best fix: (1) delete the dead log_id ternary and just call _is_gap.
    (2) Broaden gap detection (e.g. also flag Access-by-non-holder, and time
    gaps beyond a threshold with no Transfer). (3) Replace the constant location
    criterion with something real (e.g. re-weight to three live criteria, or
    derive a location signal from the surrounding custody locations). (4) Add
    unit tests with a deliberately gapped chain to prove it fills correctly.
    Justification: makes the heuristic genuinely multi-criteria and testable,
    which is what "complex logic implemented by me" is graded on.

L2. Risk-scoring interaction bonus can double-count and is hard to defend
    Where: risk_scoring.py:444-470 _detect_interactions.
    Problem: bonus = base_score*(mult-1)*avg(a,b) is added per fired rule, and up
    to five rules can fire and stack, then final is clamped to 1.0. Because
    integrity_status is stuck at 0.5 (C2) and role_mismatch/duplicate are
    mislabeled (C3), the rules that DO fire fire for the wrong reasons.
    Why bad: the interaction model is the part you claim lifts this above "a
    formula"; right now it amplifies mismeasured signals.
    Best fix: fix C2/C3 first (so the inputs are real), then cap the total
    interaction bonus (e.g. take the max single interaction, or cap cumulative
    bonus) so a few co-firing rules can't saturate every item to CRITICAL.
    Document the weight/threshold calibration. Justification: an interaction
    model is only meaningful if its inputs are correct and its output is bounded
    and explainable.

L3. Anomaly detection re-fits an Isolation Forest on every page load
    Where: anomaly_detection.py run(); called from risk.py dashboards and
    risk.py evidence_risk (twice per item view).
    Problem: the model is fitted fresh from current data on each request, with
    fixed contamination=0.2 (assumes exactly 20% anomalies regardless of data),
    and is not persisted. The proposal describes a model "fitted on baseline
    activity" — there is no baseline; it's per-request. Results shift as data
    grows and differ between the two fits done on a single evidence-risk page.
    Why bad: not reproducible; scientifically it's just flagging the relative
    tail of whatever is currently in the DB. Also a performance cost (P1).
    Best fix: fit once on a defined baseline, persist the fitted model (joblib),
    and score against it; or, if keeping it live, drop contamination to 'auto'
    and cache the result per request. Be explicit in the report that it's an
    unsupervised relative-outlier flag, not a trained detector. Justification:
    aligns the implementation with the proposal's "baseline" language and makes
    it reproducible.

L4. AI intent classifier is brittle keyword-frequency with confidence*2 hack
    Where: ai_assistant.py:106-160.
    Problem: confidence = min(1, best/total*2) is an arbitrary scaling; keyword
    overlap between CASE_QUERY and EVIDENCE_QUERY ("case"/"evidence") means ties
    resolve by dict order (max() picks the first max). Entity-ID regex
    `(?:case|evidence|item|id)[^\d]{0,5}(\d+)` will grab a number after the word
    "id" anywhere, and treats "case 3 vs evidence 7" as a single id.
    Why bad: fine for a demo, but a grader asking "why this classification?" will
    expose the hand-waving.
    Best fix: keep it (it's legitimately your own code and category C is about
    the orchestration, not ML accuracy) but (a) make tie-breaking explicit,
    (b) document the confidence heuristic honestly rather than presenting it as
    calibrated, (c) add a couple of unit tests pinning expected intents.
    Justification: honesty + tests convert a weak-looking heuristic into a
    defensible design decision.

L5. verify_integrity auto-flag silently fails for non-privileged roles
    Where: custody.py:212-217. On a Broken verdict it calls
    sm.transition_to('Flagged'), which requires Admin/Lead. An Analyst verifying
    a broken item: the flag is rejected, _log_rejection writes a confusing
    'Failed Attempt' audit row, and the return value is ignored.
    Why bad: broken evidence viewed by an analyst is NOT flagged, and the audit
    trail gains a misleading "rejected transition to Flagged" entry attributed to
    the analyst.
    Best fix: perform the auto-flag as a system action (bypass role check for
    automatic integrity-driven flagging) or check the role first and, if the
    user can't flag, still record a system-level Flag. Justification: automatic
    safety actions shouldn't depend on who happened to trigger the check.

DATA MODEL / API / MISC
--------------------------------------------------------------------------------

A1. Orphan template + missing self-service: register.html exists, no route
    Where: templates/auth/register.html; no auth.register route.
    Impact: dead file that implies a signup flow that doesn't exist (accounts are
    admin-created only, which is a fine design). Remove the template or add the
    route. Low severity but looks unfinished.

A2. _ensure_schema uses raw SQLite ALTER TABLE — breaks the "PostgreSQL-ready"
    claim. Where: __init__.py:110-169. The hand-rolled ALTERs and the enum
    handling are SQLite-flavoured; the proposal/README claim PostgreSQL
    readiness. Best fix: adopt Alembic migrations (the proposal even names
    Alembic) instead of a bespoke startup migrator, or soften the Postgres claim.
    Justification: a real migration tool is the standard answer and removes the
    startup ALTER hack that also re-scans/re-encrypts all keys on every boot.

A3. Timezone strategy is "store naive local (UTC+2)". Where: utils.now_local().
    Storing local time naive means a DST change or a server move corrupts
    ordering and the Feature-1 monotonicity check. Best fix: store UTC in the DB,
    convert to local only for display (Jinja filter). Justification: this is the
    industry-standard convention and removes C7 and a class of ordering bugs.

A4. N/A event types: CustodyLog defines event types Upload/Transfer/Access/
    Verification, but the app only ever writes Upload and Transfer. "Access" and
    "Verification" custody events are never created (access is tracked only in
    AuditRecord). The reconstruction algorithm and formula checks look for access
    events in AuditRecord, which is consistent, but the unused enum values invite
    the question "where are access custody events?" Best fix: either write Access
    custody entries on file view, or remove the unused enum values and note that
    access is audit-only. Justification: model should match behaviour.

A5. Performance/scale: no pagination on evidence/custody lists; dashboards score
    every accessible item on each load (see P1). Fine at seed scale, visibly slow
    beyond a few hundred items. Best fix: paginate, and cache/persist risk +
    anomaly results instead of recomputing per request.

A6. Committed a 5 MB DEICMS_Project_Report.docx into git history (commit
    f403839) that is no longer in the tree. It bloats the repo permanently. Best
    fix: keep large binaries out of git (or use git-lfs); if size matters, the
    history can be rewritten to drop it. Low severity.

A7. Tests exist (178 test functions across 7 files, README claims ~79% coverage)
    but could not be executed in this review environment (pytest not installed
    in the sandbox; a full dependency install timed out). Action for you: run
    `pytest -q --cov=app` locally and confirm the suite is green against the
    CURRENT code, because several bugs above (C1-C3) suggest some tests may be
    asserting on the wrong-but-consistent behaviour (e.g. counting Warning rows).
    Justification: a passing suite that locks in a bug is worse than no test.


================================================================================
PART 4 — BRUTAL, HONEST ARCHITECTURE & DESIGN REVIEW
================================================================================
You asked for no sugar-coating. Here it is, but note the headline: this is a
strong project. The criticism is about the gap between what it CLAIMS and what it
DOES, which is exactly what a demanding examiner probes.

WHAT'S GENUINely GOOD
  - The layered structure (models / logic / routes / templates) is clean and
    conventional. Business logic lives in app/logic and is mostly import-free of
    Flask, so it's testable. That is the right instinct.
  - The security surface is unusually broad for a student project: CSRF, lockout,
    rate limiting, 2FA, at-rest encryption, append-only audit via ORM events,
    magic-byte upload validation, signed tamper-evident export. Breadth is real.
  - CaseAccess as a first-class permission table with a single
    accessible_case_ids() helper reused by dashboard/risk/AI is a genuinely good
    access-control design — consistent least-privilege enforcement in one place.
  - The category A/B/C balance is defensible and the mapping is honest on paper.
  - The signed-ZIP export with manifest + public key + verification instructions
    is a nice, real, end-to-end integrity story.

THE HARD TRUTHS
  1. Several "complex" features do LESS than advertised.
     - Graph integrity does not verify per-node hashes (C4); it's really "hash
       the file once + verify signatures + check timestamps". Still worthwhile,
       but not what the proposal sells.
     - Risk scoring's top factor is a dead constant (C2) and two more factors are
       mislabeled proxies (C3). So the "multi-factor, interaction-aware" engine
       is, today, partly measuring artefacts of its own audit logging.
     - Reconstruction has two of four scoring criteria that are effectively
       constant or rarely-triggered (L1).
     If an examiner traces ONE algorithm to its data source, they'll find the
     seam. Fixing C2/C3/C4/L1 converts these from "looks complex" to "is
     complex", which is the difference between grades.

  2. Claim/implementation drift is the project's biggest risk, not any single
     bug. The proposal, README, and docstrings describe an idealised system;
     the code is ~85% of it. Graders reward honesty about limitations far more
     than they punish scoped-down scope. Right now the docs over-promise
     (per-node hashing, trained baseline anomaly model, write-protected file
     store, rejection auditing) in ways the code doesn't meet. Align the words to
     the code (or the code to the words) everywhere.

  3. The AI assistant is architecturally the nicest piece (6 clean stages,
     hallucination cross-check, access-scoped retrieval) BUT it has the one XSS
     hole (S3) and its intent classifier is hand-wavy (L4). The orchestration is
     legitimately your own work and is your strongest category-C claim — protect
     it by fixing the XSS and adding a few tests.

  4. Time and identity handling is inconsistent (naive local vs aware UTC, C7/A3).
     For a system whose ENTIRE value proposition is trustworthy timestamps and
     ordering, this is the most thematically damaging weakness. Standardise on
     UTC-in-DB. This is the single change I'd prioritise for narrative coherence.

  5. Persistence & scale were not design goals (per-request scoring, Isolation
     Forest re-fit, no pagination, SQLite, in-memory rate limiter). That's fine
     for a course demo — but don't claim "PostgreSQL-ready / production" without
     caveats (A2), because the startup ALTER-TABLE migrator and per-request
     compute say otherwise.

DESIGN IMPROVEMENTS I WOULD MAKE (not yet implemented — your call)
  D1. Introduce a service layer boundary: routes are doing DB writes + audit +
      business logic inline. Extract "record custody transfer", "run integrity
      check", "score evidence" into logic/services that own their own
      transaction and audit writes. This removes the C5/C6-style transaction bugs
      (commit-vs-rollback mistakes) by centralising the commit boundary.
  D2. Make audit writing a helper (audit(event, ...)) instead of hand-building
      AuditRecord in ~30 places. Reduces copy-paste drift (e.g. the mislabeled
      result='Warning' in C3 came from ad-hoc audit writes).
  D3. Persist derived results (risk_score/level already on the row; also cache
      last integrity verdict + anomaly score) and recompute on write, not on
      read. Turns the dashboards from O(N * queries) into simple reads.
  D4. Replace the bespoke _ensure_schema migrator with Alembic (already in the
      proposal's stack). One honest migration story.
  D5. Add a integrity_status column and wire the integrity->risk->flag loop end
      to end. This single thread (verify updates status -> status feeds risk ->
      broken auto-flags -> flag feeds risk) is the project's core narrative;
      right now the links are broken (C2/C4/L5). Closing this loop is the highest-
      value design fix.
  D6. Decide the timezone convention once (UTC in DB) and enforce with a Jinja
      display filter. Thematically essential for a chain-of-custody system.
