# Part VI — Cross-Cutting Quality

The three increments and the two maintenance iterations were narrated chronologically in Parts II through V. This part steps out of that chronology to treat three concerns that run across the whole system and are better understood in consolidated form than scattered through the increment chapters: the testing strategy and what its coverage does and does not establish, the security engineering that pervades the architecture, and a self-assessment of how the delivered features balance across the three required feature categories.

## 22. Testing Strategy and Coverage Analysis

### 22.1 Testing Philosophy

The testing on this project was shaped by a single guiding idea: the parts of the system most likely to be wrong, and most costly if wrong, should be given the most direct and the most adversarial tests. In a chain-of-custody system the parts most costly if wrong are the algorithms that decide whether an item's history is intact and how risky it is, and the authorisation logic that decides who may see what. The test suite therefore concentrates its effort on the business-logic layer and on the authorisation boundaries, and treats the thin route handlers and the templates more lightly, because a defect in a route that merely wires an engine to a template is both less likely and less damaging than a defect in the engine or in an access check.

The tests are predominantly **example-based unit tests** at the level of the logic modules, supplemented by **integration tests** that drive the system end to end through its HTTP interface, and by a dedicated body of **adversarial authorisation tests**. This distribution gives the suite roughly the shape of the classic test pyramid: many fast, isolated unit tests over the algorithms; a smaller number of slower integration tests over the full request-to-response path; and a focused set of tests that probe the security boundaries. The suite runs in well under two minutes in its entirety and requires no external services, because the one external dependency — the language model — is invoked through a seam that the tests replace with a deterministic mock.

### 22.2 Organisation of the Suite

The suite is organised to mirror the project's structure, which makes a failure easy to localise. There is one test module per increment — the first increment's models and CRUD, the second's state machine and integrity and reconstruction algorithms, the third's risk scoring, anomaly detection, and assistant pipeline — plus a day-two module covering the cryptographic key generation and the audit formula checks that accompanied the first increment. Beyond the increment modules, an **integration module** exercises the complete workflows an investigator actually performs: logging in, creating a case, uploading and transferring evidence, running verification and reconstruction, exporting the signed package, downloading the PDF report, and editing the risk settings. A **scoping module** holds the adversarial authorisation tests introduced in maintenance iteration M1. An **intent-classifier module** pins the assistant's intent-ranking behaviour introduced in M2. In total the suite comprises one hundred and seventy-two tests, all passing.

### 22.3 Two Practices That Shaped the Suite

Two practices, both adopted as retrospective actions and both discussed in the increment chapters, are visible in the shape of the coverage. The first is **test-first development of the complex algorithms**, adopted after Increment 2. The risk-scoring tests, for example, exercise the normalisation curves directly and were written before the scorer was implemented, which is why they include the degenerate cases — equal normalisation bounds, a negative input to the logarithmic curve — that an after-the-fact test tends to miss; writing the acceptance criteria as tests first turned "the score must be in range" and "all failures must be found" from prose into executable checks that the implementation then had to satisfy. The second is the **mock seam over the language model**. Because the assistant invokes the model through a single method that falls back to a context-aware mock when no key is configured, every one of the pipeline's six stages — intent classification, context retrieval, prompt construction, the model call, response validation, and hallucination detection — is testable without a network call, which is what made the assistant, ordinarily the hardest part of a system to test, one of the better-covered.

### 22.4 Coverage Analysis

Measured across the application package, the suite covers approximately **seventy-eight per cent of statements**. That headline figure is less informative than its distribution, which is exactly what the testing philosophy predicts: the layers that matter most are covered most. Table 22.1 gives the coverage of the components that carry the system's essential logic.

**Table 22.1 — Statement coverage of the core logic and data layers**

| Module | Coverage |
|---|---|
| Risk scoring (`risk_scoring`) | 97% |
| Anomaly detection (`anomaly_detection`) | 100% |
| Graph integrity verifier (`graph_integrity`) | 90% |
| Audit formulas (`audit_formulas`) | 94% |
| Cryptography (`crypto`) | 95% |
| Evidence lifecycle state machine (`state_machine`) | 83% |
| AI assistant orchestration (`ai_assistant`) | 78% |
| Custody chain reconstruction (`chain_reconstruction`) | 65% |
| Data models (Evidence, Case, Custody, Case Access, …) | 88–97% |
| Dashboard route | 98% |

The pattern is clear and intended. The five complex algorithms and the cryptographic and formula code — the Category C and the security-critical work — are covered in the high eighties to one hundred per cent, with the single exception of the chain reconstructor at sixty-five per cent, whose lower figure reflects the many candidate-scoring branches that only execute for particular gap configurations and that the test scenarios do not all reproduce. The data models are covered in the high eighties to high nineties. The coverage that is *not* achieved is concentrated in the route handlers and in defensive error branches — the paths taken when an external service is unavailable, when a file is missing, or when a rarely-reached validation fails — and in the templates, which are exercised by the integration tests for their happy paths but not for every conditional. This is the appropriate place for coverage to thin: a report that claimed one hundred per cent would be claiming to test glue code and error branches whose failure modes are low-risk, at a cost in test-maintenance that would not be repaid.

### 22.5 What the Coverage Does and Does Not Establish

It is worth stating plainly what this testing establishes and what it does not, because an honest account of quality is more valuable than an inflated one. The suite establishes that the algorithms compute what their acceptance criteria require across the normal and the degenerate cases the tests describe; that the full investigator workflows function end to end; that the authorisation boundaries hold against the adversarial scenarios the scoping module constructs; and that a change which breaks any of these will fail the suite, so the suite serves its primary purpose as a regression guard. It does not establish that the system is free of defects — maintenance iteration M2 is itself proof that a green suite can coexist with real bugs, since two critical defects survived it — and it does not exercise concurrency, load, or the behaviour of the live language model. Those limits are acknowledged rather than hidden, and the project's response to them is the complementary practice, drawn from M2, of periodic code review to catch the class of defect that testing structurally misses.

## 23. Security Engineering

### 23.1 A Defence-in-Depth Posture

Security is the quality that matters most for a system whose entire purpose is to be trustworthy, and in DEICMS it is engineered as a property distributed across every layer of the architecture rather than concentrated in any single control. The design goal is **defence in depth**: the compromise or failure of any one control should not by itself defeat the system. The controls are organised by the layer at which they operate — transport, session, request, authorisation, data, and integrity — and each layer defends against a distinct class of threat, so that an attacker must defeat several independent mechanisms rather than one.

### 23.2 The Controls by Layer

At the **transport** layer the application serves only over HTTPS, using a certificate generated on first run, and sends an HTTP Strict-Transport-Security header so that a browser that has once connected securely will refuse to fall back to plaintext, defending against downgrade and passive interception. At the **session** layer, authentication is managed by Flask-Login and hardened with optional time-based one-time-password two-factor authentication, a sliding idle-session timeout, and account lockout after repeated failed logins, so that a stolen or guessed password does not by itself grant lasting access. At the **request** layer, cross-site-request-forgery protection is applied to every state-changing form, the login route is rate-limited against brute forcing, and — from maintenance iteration M2 — a Content-Security-Policy together with the `X-Content-Type-Options`, `X-Frame-Options`, and `Referrer-Policy` headers provides defence in depth against script injection and clickjacking, complementing the escaping of untrusted model output that closed the stored cross-site-scripting vector in the chat.

At the **authorisation** layer, every route enforces a minimum role, and every access to case data is checked against the requesting investigator's case membership through the single `accessible_case_ids` rule introduced in M1 — a check that applies not only to direct record access but, crucially, to every aggregate view and to the AI assistant's data retrieval, so that no surface of the system leaks across the case boundary. At the **data** layer, evidence files are encrypted at rest with AES-256-GCM; investigators' private keys are themselves encrypted with a Fernet key derived from the application secret, so that a database compromise alone yields no usable signing keys; and uploads are validated by their magic bytes so that a renamed executable cannot masquerade as an image. At the **integrity** layer, every custody event is signed with Ed25519 so that it cannot be forged or repudiated, the audit trail is append-only and enforced as such at the object-relational-mapping layer so that history cannot be rewritten, and the graph verifier can prove cryptographically that an item's whole custody history is intact.

### 23.3 Cryptographic Design

The cryptographic choices are conventional and deliberately so, because a forensic system is not the place to innovate in cryptography. Integrity uses **SHA-256**, computed on the plaintext at intake and recomputed against the decrypted file during verification. Non-repudiation of custody events uses **Ed25519** signatures over a canonical, sorted-key serialisation of the event's fields, a modern elliptic-curve scheme chosen for its strong security margin and small keys. Confidentiality of stored evidence uses **AES-256-GCM**, an authenticated mode that provides both secrecy and tamper-detection of the ciphertext. Private keys are protected at rest with **Fernet**, an authenticated symmetric construction, under a key derived from the application secret, so that the keys usable to sign on an investigator's behalf are never stored in a directly usable form. The single most important operational caveat, and one the code surfaces honestly, is that the key-encryption secret must not be rotated after data exists, because doing so would render every encrypted file and private key unrecoverable; the system emits a startup warning when it is running under the insecure development default for this secret precisely so that the condition cannot pass unnoticed into a real deployment.

### 23.4 The Security Contribution of the Maintenance Iterations

It is fair to record that the security posture described here was not fully present at the end of Increment 3, and that the two maintenance iterations materially improved it. M1 closed a pervasive authorisation leak in which every aggregate view and the assistant exposed data across case boundaries, and it did so by introducing the single scoping rule that the whole system now shares. M2 closed a cross-case insecure-direct-object-reference on the evidence routes, a stored cross-site-scripting vector in the chat, and the absence of a content-security policy, and it added the startup warnings for insecure default secrets. That these were found and fixed is a strength of the process rather than an embarrassment: a security posture that is arrived at through deliberate review and adversarial testing, with the gaps documented, is more trustworthy than one merely asserted to have been correct from the start.

### 23.5 Acknowledged Limitations

Consistent with the report's commitment to honesty, the security engineering has limits that are stated rather than concealed. The TLS certificate is self-signed and suitable for local demonstration, not for a public deployment. The Content-Security-Policy still permits inline scripts and styles because the templates embed them, and tightening it to a nonce-based policy is recorded as a known next step rather than claimed as done. The application ships with insecure default secrets that must be replaced before any real use, which the startup warnings make conspicuous but do not prevent. And the system has not been subjected to load or penetration testing. These are the appropriate limitations for an academic project that demonstrates security engineering rather than operating a production evidence store, and naming them is part of demonstrating that engineering maturely.

## 24. Feature Categorisation Self-Assessment

### 24.1 The Requirement and the Method

The coursework requires that the system's functionality be categorised into three kinds — data/repository, third-party services, and complex application logic — and that the proposal be balanced across them, with the reasoning made explicit. This chapter assesses the delivered system against that requirement. The method, applied from the proposal onward, was to assign each feature to exactly one category on the basis of where its *essential difficulty* lies, resisting the temptation to inflate the complex-logic category by claiming library work as one's own, and the assessment below is a self-critical audit of whether that balance was in fact achieved.

### 24.2 What Was Delivered in Each Category

**Category A — data / repository.** The delivered data layer is a relational model of six entities — Investigator, Case, Evidence Item, Custody Log, Audit Record, and Case Access — with full create-read-update-archive operations, case-level search, an append-only audit trail enforced at the persistence layer, and the three formula-based audit checks for custody time-gaps, duplicate entries, and role mismatches. This is a substantial data layer rather than a token one: the six entities and their relationships encode real domain rules, and the append-only enforcement and the formula checks are genuine data-oriented engineering rather than bare CRUD.

**Category B — third-party services.** The delivered third-party integrations are numerous and varied: SHA-256 hashing, Ed25519 signing and AES-256-GCM encryption from the `cryptography` library, EXIF and magic-byte metadata extraction from Pillow and python-magic, the SQLAlchemy object-relational mapper, the Llama 3.1 language model consumed through the NVIDIA NIM API, the scikit-learn Isolation Forest, ReportLab PDF generation, and PyOTP two-factor authentication. In each case the report is careful, in the relevant chapter, to distinguish what the library provides from what the surrounding application logic contributes — the hashing algorithm from the registration workflow, the signature primitive from the canonical-payload design, the language model from the orchestration pipeline.

**Category C — complex application logic.** The delivered complex logic comprises five items implemented from scratch: the chain-of-custody graph integrity verification algorithm, the multi-factor evidence risk-scoring algorithm, the custody-chain reconstruction algorithm, the evidence lifecycle state machine, and the AI investigation assistant's orchestration workflow. Each involves a custom data structure, a multi-step algorithm with branching logic, or a heuristic search that cannot be reduced to a query, a formula, or a library call, and each was given an algorithmic account in the increment chapters sufficient to demonstrate that complexity rather than merely assert it.

### 24.3 Is the Balance Genuine?

The honest assessment is that the balance is genuine and, if anything, richer than the minimum the coursework requires. No single category carries the system: the data layer is not a thin veneer over the algorithms, the third-party integrations are not a single decorative API call, and the complex-logic layer is not one algorithm padded out with claims. A useful test of whether a complex-logic claim is real is to ask whether the feature could have been bought as a library; for all five Category C items the answer is no — there is no library that verifies a bespoke custody graph against this schema, scores risk against these eight factors and interaction rules, reconstructs gaps with this plausibility model, enforces this lifecycle, or orchestrates a language model against this access-scoped context with this hallucination check.

The most persuasive evidence that the categorisation was approached with genuine rigour rather than as a labelling exercise is the deliberate **integration across categories** that emerged during the maintenance work. The two risk factors for duplicate entries and role mismatches were changed to compute their values by calling the Category A audit-formula checks live, so that the simple Category A formulas became inputs to the complex Category C scoring algorithm. This was not necessary to make either category "count" — each stood on its own — but it produced a system in which the categories reinforce rather than merely coexist, which is a stronger design than three isolated silos and is exactly the kind of relationship the categorisation exercise is meant to encourage.

### 24.4 Where the Categories Were Kept Honest

Finally, it is worth recording the places where the temptation to inflate a category was consciously resisted, because that restraint is itself part of a fair categorisation. The language model, the Isolation Forest, and the cryptographic primitives were kept firmly in Category B, with only the orchestration, the feature engineering, and the protocol design around them claimed as Category C — the assistant's pipeline is complex, but the model is not the project's; the anomaly detection's feature vector is the project's, but the Isolation Forest is not. The graph verifier's hash and signature checks call Category B libraries, but they do so as primitive operations inside an algorithm the project designed, in the same way arithmetic operators sit inside a formula, and the report says so rather than claiming to have implemented SHA-256 or Ed25519. And where a piece of behaviour turned out to be simpler than a complex-logic claim would require — the sequential numbering of cases and evidence, for instance — it was described as the straightforward data operation it is rather than dressed up. This restraint is what makes the Category C claims credible: a categorisation that never declines to claim complexity is not a categorisation at all, and the value of this one is that it draws the line where the code actually draws it.
