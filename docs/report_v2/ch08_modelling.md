## 8.1 Why Model a System

System modelling is the process of developing abstract models of a system, with **each model presenting a different view or perspective** of that system. In current practice it means representing a system using a graphical notation, almost always based on the **Unified Modeling Language (UML)**.

Modelling is an application of the principle of abstraction (Section 3.6): a model identifies the important aspects of the system and ignores the rest. Because different questions require different things to be ignored, no single model can serve every purpose — which is why a complete description requires several diagrams rather than one large one. A map of a city is the standard illustration: the city is the system, the map is a model, its legend is the notation, and different maps of the same city serve different purposes without contradicting one another.

Models are used for three distinct purposes, and it is worth naming which apply here.

**Table 8.1 — Purposes of modelling, and their role in this project**

| Purpose | Description | Used in DEICMS? |
|---|---|---|
| **Discussion** | Models as a means of communicating about the system with stakeholders | Yes — the models are how this report explains the system to a reader who will not read the source |
| **Documentation** | Models as a record of an existing or planned system | Yes — the primary use here; models were drawn during design and kept in step with the code under version control |
| **Code generation** | Generating a partial implementation automatically from the model, as in Model-Driven Engineering | No — models informed the code but did not generate it, and this is stated rather than implied |

Model-Driven Engineering takes the third purpose furthest, treating models as the primary artefacts from which software is generated by model-to-model and model-to-text transformations, summarised as *models plus transformations equals software*. DEICMS does not practise MDE; its models are design and documentation artefacts. This is recorded explicitly because a report that shows UML diagrams without saying how they relate to the code leaves the reader to guess whether the code was generated, and the honest answer here is that it was not.

### 8.1.1 The Four Modelling Perspectives

A system may be modelled from four perspectives, and DEICMS provides a model from each.

**Table 8.2 — Modelling perspectives**

| Perspective | Question answered | Diagram type | DEICMS figure |
|---|---|---|---|
| **External / context** | What is the system's environment, and who interacts with it? | Use case | Figure 8.1 |
| **Structural** | How is the system organised — what are its parts and how do they relate? | Class, entity-relationship, component | Figures 8.3, 8.3, 8.9 |
| **Interaction** | How do the parts communicate to achieve a task? | Sequence | Figures 8.5, 8.5 |
| **Behavioural** | How does the system respond to events and stimuli over time? | Activity, state machine | Figures 8.7, 8.7, 8.8 |

### 8.1.2 UML Diagram Taxonomy

UML diagrams divide into two families. **Structural diagrams** describe what the system *is* — its static composition, which does not change as the system runs. **Behavioural diagrams** describe what the system *does* — its dynamics over time.

**Table 8.3 — The UML diagrams used in this report, by family**

| Family | Diagram | Shows | Figure |
|---|---|---|---|
| Structural | Class diagram | Classes, their attributes and operations, and the associations between them | 8.2 |
| Structural | Entity-relationship diagram | Database tables, columns, keys and cardinalities | 8.3 |
| Structural | Component diagram | The system's modules and the interfaces between them | 8.9 |
| Structural | Deployment diagram | The physical nodes and the artefacts deployed on them | 8.10 |
| Behavioural | Use case diagram | Actors and the services the system offers them | 8.1 |
| Behavioural | Sequence diagram | Messages exchanged between objects, ordered in time | 8.4, 8.5 |
| Behavioural | Activity diagram | Control flow through an activity, with decisions and concurrency | 8.6, 8.7 |
| Behavioural | State machine diagram | States of an object and the events that move it between them | 8.8 |

The entity-relationship diagram is strictly speaking not UML but a distinct notation; it is included because the professor's diagram set requires it and because a relational system's data model is better expressed in ER notation than as a class diagram with stereotypes. The relationship between the two — the class diagram is the object model, the ER diagram is its relational realisation through the ORM — is discussed in Section 8.5.

All diagrams were produced in **PlantUML**, a text-based notation from which the diagram is rendered, and their sources are kept under version control alongside the code in `diagrams_plantuml/`. This choice serves two of the report's aims: a text source produces a visible diff when the model changes, which is what prevents diagrams drifting silently away from the code they describe (Section 6.5); and it renders in a single colour, so that the diagrams carry no information in colour that would be lost in a monochrome print or when redrawn by hand.

## 8.2 Context and Use-Case Models

The use-case model takes the **external perspective**: it shows the boundary of the system, the actors outside it, and the services it offers them. It answers *who uses this system and what for?* and deliberately says nothing about how any of it works.

The system has **forty-one use cases**, which is too many for one readable diagram — and readability matters here for a practical reason: a diagram that cannot be redrawn by hand is not a communication artefact. The model is therefore split across two figures along the natural seam between *working with evidence* and *analysing and administering it*, and both use **actor generalisation** to exploit the strict nesting of role capability established in Table 8.6.

**[FIGURE 8.1 — Use Case Diagram (a): Authentication, Cases, Evidence and Custody]**

**[FIGURE 8.2 — Use Case Diagram (b): Analysis, Reporting, Assistant and Administration]**

Four actors correspond exactly to the four roles of the access-control model and the four personas of Section 7.2, and they are connected by **generalisation** rather than drawn independently: the Analyst generalises the Read-Only Auditor, the Lead Investigator generalises the Analyst, and the Administrator generalises the Lead Investigator. Each actor is therefore joined only to the use cases it **adds** to the role beneath it, and inherits the rest.

This is the correct UML construction for a nesting role model and it has a large practical benefit: instead of 116 association lines it needs 33, and the inheritance triangles themselves communicate the policy — *an Administrator can do everything a Lead can, and more* — which a flat diagram states only by exhaustion.

Two relationship types appear. The **«include»** relationships show behaviour that is always part of the including use case: registering evidence, transferring custody and verifying integrity all include an authenticated session, because none can occur without one; exporting a signed package includes verifying integrity, because the export is worthless if the chain it certifies has not been checked. The **«extend»** relationship shows optional behaviour: reconstructing a custody chain extends verification, because reconstruction is invoked only when verification reveals gaps.

The second figure repays a moment's attention for what it does *not* contain: the Analyst adds **no** use case there at all. Analysis and reporting are read activities available to every role within its accessible cases, so the Analyst's two extra capabilities over the auditor — UC-18 and UC-23 — are both custody actions and both appear in the first figure. That asymmetry is the domain's own logic made visible.

The diagrams also encode the least-privilege model **negatively — by what is absent**. No line runs from the Analyst or the Read-Only Auditor to any administration use case; no line runs from the Read-Only Auditor to any use case that creates, modifies or deletes a record; and no actor at all connects to a registration use case, because none exists (FR-21). These absences are as much a part of the specification as the lines that are present.

### 8.3.4 Two Findings from Deriving This Catalogue

Building the catalogue from the guards rather than from the design intent produced two observations worth recording, because both are the kind of thing a use-case model is supposed to surface.

**The Analyst cannot upload evidence.** UC-14 is guarded by `can_manage()`, which admits only Admin and Lead Investigator. The persona description of Nadia the Analyst (Table 7.3) says she "works on the evidence within the cases she is assigned to" — which is consistent — but an earlier draft of the user requirements had her registering evidence, and that draft was wrong about the system. The code is the stricter and, on reflection, the more defensible position: registration is the moment an item enters the chain of custody, and restricting it to Lead Investigators keeps intake accountable to case ownership. The requirement (UR-10) has been corrected to match.

**A Read-Only auditor can trigger integrity verification, and verification writes to the database.** UC-20 carries no role guard, so an auditor may run it; and since M2 (finding D2) a verification writes the item's `integrity_status` back so that the risk scorer can read it. Strictly, therefore, a "read-only" role can cause a database write.

This is defensible and is not a defect: verifying a chain of custody is precisely what an auditor exists to do, the write is a derived status rather than substantive data, no evidence content or custody record is altered, and the verification is itself audited. But the role's *name* over-promises, and the honest statement is that Read-Only means **may not create, modify or delete a record**, not that the role has no effect on the database whatsoever. The report states it that way rather than leaving the name to imply more than the code delivers.

## 8.4 Structural Model: the Class Diagram

The class diagram takes the **structural perspective** on the application's object model: the classes, their attributes and operations, and the associations between them with their multiplicities.

**[FIGURE 8.3 — Class Diagram]**

Six classes correspond to the six domain entities. Three features of the model are worth drawing out, because each encodes a requirement rather than merely a fact about the code.

**Composition versus association.** The diagram distinguishes *composition* (filled diamond, meaning the part cannot exist without the whole) from plain *association*. A Case composes its Evidence Items and an Evidence Item composes its Custody Logs: an evidence item has no meaning outside a case, and a custody record has no meaning outside the item it describes. By contrast, Audit Records are merely *associated* with the entities they reference, which is deliberate — an audit record must survive the entities it mentions, because the record of what happened to a deleted item is precisely the evidence that must not be destroyed (domain requirement DR-04). The choice of relationship type here is therefore a design decision with a legal justification, not a notational preference.

**Multiplicity encoding an invariant.** The Evidence Item to Custody Log association is `1 .. 1..*`, not `1 .. 0..*`. An evidence item must have *at least one* custody record. This is requirement FR-12 — the first custody entry is created atomically with the item — expressed in the model, and it is the invariant that makes the graph integrity verifier's assumption of an upload root safe.

**Two associations between the same pair.** Investigator relates to Evidence Item twice, as *uploader* and as *current holder*, and to Custody Log twice, as *from* and *to*. Labelled association ends are what make such a model readable; without them the diagram would state that investigators and evidence are related without saying how.

The operations shown are limited to those that carry domain meaning — `verify_signature()`, `compute_hash()`, `accessible_case_ids()` — rather than every accessor. A class diagram that lists every getter documents the language, not the design.

## 8.5 Data Model: the Entity-Relationship Diagram

Where the class diagram models objects, the entity-relationship diagram models the **relational realisation** of those objects: tables, columns with their SQL types, primary and foreign keys, and cardinalities in crow's-foot notation.

**[FIGURE 8.4 — Entity-Relationship Diagram]**

The two diagrams describe the same six entities and are related by the object-relational mapping (Section 9.3): the ORM is what makes the class model and the table model two views of one thing rather than two separate designs to be kept in step manually. Where they differ, the difference is informative.

**Table 8.10 — Where the class model and the relational model differ**

| Aspect | Class diagram | ER diagram | Reason |
|---|---|---|---|
| Associations | Shown as lines with multiplicity | Realised as foreign-key columns | The relational model has no direct notion of an association |
| Types | Conceptual (String, Integer) | Concrete SQL (`VARCHAR(150)`, `CHAR(64)`, `BIGINT`) | Storage requires committed widths |
| Constraints | Implicit in multiplicity | Explicit `NOT NULL`, `UNIQUE`, `PK`, `FK` | Enforced by the database, not by convention |
| Behaviour | Operations shown | Absent | Tables have no methods |

Three modelling decisions in the schema deserve comment.

**`original_hash` and `current_hash` are separate columns.** A single `hash` column would be simpler and wrong: the original hash is the fingerprint at intake and must never change, while the current hash tracks the latest verified state. Integrity verification is precisely the comparison of the two, so collapsing them would destroy the system's central capability. This is guarantee G1 realised in the schema.

**`digital_signature` is `NOT NULL`.** An unsigned custody record cannot be represented. This is requirement FR-24, and it is enforced at the strongest available level — the database constraint — rather than by application logic that could be bypassed.

**`CASE_ACCESS` is an associative entity, not a column.** Case membership could have been modelled as a column on the investigator, but that would permit exactly one case per investigator. The associative table resolves the many-to-many relationship and additionally carries attributes of the *relationship itself* — the permission level, when access was granted and by whom — which have nowhere to live in either of the entities it joins. It is also, as Section 5.4 records, the single table that made the M1 fix possible.

## 8.6 Interaction Models: Sequence Diagrams

Sequence diagrams take the **interaction perspective**, showing the messages exchanged between participants ordered down the vertical time axis. They answer *how do the parts cooperate to achieve this?* — a question neither a structural nor a purely behavioural diagram can answer.

### 8.6.1 Chain-of-Custody Integrity Verification

**[FIGURE 8.5 — Sequence Diagram: Integrity Verification]**

Six participants appear: the Analyst, the integrity route, the verification engine, the database, the file store and the cryptographic primitives. The diagram shows the route performing authorisation *before* delegating, then the engine loading the item and its ordered custody logs, building the graph, and entering the traversal loop.

Two aspects of this diagram carry design information that prose states less clearly.

The **loop fragment** makes visible that the three checks — hash continuity, signature validity, timestamp monotonicity — occur at *every node*, and that the failure accumulation step sits inside the loop rather than terminating it. The note "do not stop" records the design decision described in Section 5.2.5: the traversal was initially written to short-circuit at the first failure and had to be reworked, because a forensic verifier that reports only the first problem is much less useful than one that locates all of them.

The **separation of the file store from the database** makes visible that verification re-reads and re-hashes actual file content rather than comparing two stored values. This is the verifiability-over-performance trade-off recorded in Section 2.5 — a cached integrity result is not an integrity proof — and the diagram is where that decision becomes legible.

### 8.6.2 AI Assistant Orchestration

**[FIGURE 8.6 — Sequence Diagram: AI Assistant Orchestration]**

This diagram traces the six-stage pipeline from question to validated answer, and it is the clearest visual statement of what makes the assistant a Category C feature rather than a Category B one. The call to the language model is a **single message in the middle of the diagram**; the five stages surrounding it — intent classification, access-scoped retrieval, prompt construction, response validation, hallucination detection — are the application's own work.

The **alt fragment** around the model invocation documents the robustness behaviour added in M2: if the model responds, its reply is used; if it has been retired or times out, the next candidate is tried; if all candidates fail, the pipeline falls back to a context-aware mock. The system therefore has no state in which the assistant simply fails.

The annotation on the retrieval message — *scoped by `accessible_case_ids`* — is the M1 fix in the model. Before that change the message carried no such qualifier, and the diagram would have been an accurate picture of a defect.

## 8.7 Behavioural Models: Activity Diagrams

Activity diagrams take the **behavioural perspective** on a single activity, showing control flow through actions, decisions, merges and concurrency. They are the appropriate notation for an algorithm whose interest lies in its control structure rather than in the collaboration between objects.

### 8.7.1 Multi-Factor Risk Scoring

**[FIGURE 8.7 — Activity Diagram: Multi-Factor Risk Scoring]**

The diagram is partitioned into the algorithm's five stages. The **fork and join** in stage one is used deliberately and is not decorative: the eight factor extractions are genuinely independent of one another and could execute in any order or in parallel, and the fork states that property. A sequential chain of eight actions would have implied an ordering constraint the algorithm does not have.

The **decision chain** in stage five shows the three thresholds — 0.75, 0.50, 0.25 — and the four resulting levels, and the cascading structure encodes that the bands are ordered and exhaustive.

The note that the interaction bonus is **capped** records a design decision explained in Section 11.3: several rules can fire simultaneously, and without a cap on the total bonus any moderately risky item saturates at 1.0, which destroys the ranking the score exists to produce.

### 8.7.2 Custody Chain Reconstruction

**[FIGURE 8.8 — Activity Diagram: Custody Chain Reconstruction]**

This diagram shows a heuristic search, and its distinguishing feature is the number of **paths that end in an honest admission of failure**. Three separate branches lead to a link being labelled *Unresolved*: an empty chain, a gap with no candidates, and a gap whose best candidate scores below the plausibility threshold of 0.40.

That structure is the visual form of domain requirement DR-07. An algorithm designed to look impressive would lower the threshold and always produce a complete chain; this one refuses to infer a link it cannot justify, and the note *"inferred links are never presented as confirmed"* states the obligation the diagram's shape enforces.

## 8.8 State Machine Model: the Evidence Lifecycle

The state machine diagram models an object's **lifecycle**: the states it may occupy, the events that move it between them, and the guards that constrain those movements.

**[FIGURE 8.9 — State Machine Diagram: Evidence Lifecycle]**

Six states are shown, connected by fourteen transitions. Every transition is annotated with the roles permitted to trigger it, and two carry additional **guard conditions** in guillemets.

The transition table contains **fourteen entries**; the ten rows below present them, with the five *any state → Flagged* entries collapsed into one row for readability.

**Table 8.9 — The transition table in tabular form**

| From | To | Permitted roles | Guard |
|---|---|---|---|
| *(initial)* | Collected | — | Evidence registered |
| Collected | Submitted | Admin, Lead | — |
| Collected | Transferred | Admin, Lead, Analyst | — |
| Submitted | Under Analysis | Admin, Lead, Analyst | At least one custody log entry must exist |
| Submitted | Transferred | Admin, Lead, Analyst | — |
| Submitted | Archived | Admin only | — (emergency path) |
| Under Analysis | Transferred | Admin, Lead, Analyst | — |
| Under Analysis | Archived | Admin, Lead | A passed integrity check (verdict Intact) is required |
| Transferred | Under Analysis | Admin, Lead, Analyst | — |
| *any state* | Flagged | Admin, Lead | — (entered on integrity failure) |
| Flagged | Under Analysis | Admin only | — (after the issue is resolved) |

Three properties of this automaton are worth stating because they are what make it a *formal* model rather than a diagram of a workflow (Section 3.3).

**Illegal transitions are decidable.** The transition table is total: a pair of states either appears in it or does not, and one that does not is refused with the exact unmet condition. There is no ambiguous case.

**The guard on archiving is the system's central procedural rule.** An item cannot move from Under Analysis to Archived unless a verification has returned Intact. This is what converts a matter of professional discipline — *check integrity before filing* — into a matter of enforced logic, and it is guarantee G4 in its purest form.

**Flagged is reachable from every state and escapable from only one.** Any state can be flagged when integrity fails, but only an Admin can move an item out of Flagged, and only into Under Analysis. This asymmetry is deliberate: an item whose integrity has failed must not quietly return to normal handling, and the diagram makes the asymmetry visible at a glance in a way that a list of rules does not.

The absence of a transition is as meaningful as its presence. There is no transition from Archived to any state except Flagged, because an archived item is closed; and a Read-Only investigator appears in no row at all, which is why the system offers such a user no available transitions rather than presenting transitions that would be refused.

## 8.9 Implementation and Deployment Models

### 8.9.1 Component Diagram

**[FIGURE 8.10 — Component Diagram: System Architecture]**

The component diagram takes the structural perspective at the level of **modules rather than classes**, showing the system's packages and the dependencies between them. Five packages are shown — presentation, routing, business logic, cross-cutting utilities and data access — together with the three external elements the system touches: the database, the encrypted file store and the inference API.

The diagram's value is that it makes the layering rule *checkable*. Dependencies run downward only: routing depends on logic, logic depends on data access, and no arrow runs from a logic component back up to a route. The one component with an outward dependency is `ai_assistant`, which reaches the NVIDIA NIM API — and the fact that exactly one component crosses the system boundary is what made the model-retirement incident of Section 5.5 a one-file change.

The diagram is also where the cross-cutting utilities are visible as such. `decorators`, the audit recorder and the time helper are depended upon from every layer, which is the definition of a cross-cutting concern and the justification for implementing each exactly once (Section 3.4).

### 8.9.2 Deployment Diagram

**[FIGURE 8.11 — Deployment Diagram: Development Environment]**

The deployment diagram shows the **physical topology**: the nodes on which the system runs and the artefacts deployed on each. Three nodes appear — the client workstation, the application host, and the cloud inference service — with the protocol on each connection.

This diagram documents the development configuration honestly rather than an aspirational production one. The server is Werkzeug with a self-signed certificate, the database is a SQLite file in write-ahead-log mode, and the evidence files are an encrypted directory on the same host. The note records the production path — PostgreSQL in place of SQLite, gunicorn behind a reverse proxy in place of Werkzeug — and states that no application code changes are required to take it, which is the portability requirement NFR-09 made concrete.

## 8.11 Summary

This chapter presented the complete model of DEICMS. It established why systems are modelled — abstraction applied so that a system can be reasoned about through a simplified representation — and distinguished the three purposes of modelling, stating explicitly that this project uses models for discussion and documentation but not for code generation. Four modelling perspectives and two diagram families were defined, and a diagram supplied for each.

Ten diagrams were presented: a use-case model of the system's boundary and actors, with structured descriptions of the four most significant use cases; a class diagram whose composition relationships and multiplicities encode domain requirements rather than merely describing code; an entity-relationship diagram with an account of where and why it differs from the class model; two sequence diagrams whose fragments document the failure-accumulation and model-fallback decisions; two activity diagrams, one of which is notable for the number of paths that end in an honest admission of failure; a state machine whose guard conditions convert procedure into enforced logic; and component and deployment diagrams that make the layering rule checkable and the production path explicit.

Throughout, the emphasis has been on what each diagram encodes that prose states less well — an absent arrow, a multiplicity of `1..*` rather than `0..*`, a fork that asserts independence, a note that says *do not stop*. The next chapter turns from modelling the system to the architecture those models describe.
