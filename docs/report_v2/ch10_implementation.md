# Chapter 10 — Implementation

---

## 10.1 Development Environment and Coding Standards

Implementation is the process of realising the design as a working program. This chapter documents how the architecture of Chapter 9 was constructed, organised by subsystem rather than by increment, so that a reader interested in how custody logging works need not read three chapters to find it. The complex algorithms, which warrant algorithmic rather than descriptive treatment, are held over to Chapter 11.

**Table 10.1 — Development environment**

| Aspect | Detail |
|---|---|
| Language and runtime | Python 3 |
| Operating system (development) | Windows 11; the test suite also runs unchanged on Linux |
| Editor | Visual Studio Code |
| Version control | Git, initialised before the first line of application code |
| Dependency management | `requirements.txt` with pinned versions |
| Test runner | pytest with pytest-cov |
| Local server | Werkzeug over HTTPS with a self-signed certificate generated by `generate_cert.py` |
| Database | SQLite in write-ahead-log mode; `flush_db.py` checkpoints the WAL for inspection |

**Table 10.2 — Coding standards applied**

| Standard | Rule | Purpose |
|---|---|---|
| Module responsibility | One module, one concern | Cohesion (Section 3.5) |
| Layer discipline | Routes contain no algorithms; logic modules import no framework | Separation of concerns (Section 3.4) |
| Naming | Descriptive names over abbreviations; predicates read as questions (`is_locked`, `can_analyse`) | Understandability (Section 2.4.11) |
| Docstrings | Every public function states its purpose and contract, not a restatement of its code | Understandability |
| Comments | Reserved for *why*, never *what* | A comment that repeats the code goes stale silently |
| Single source of truth | Cross-cutting rules — authorisation, audit recording, local time — implemented once | Prevents the class of defect found in M1 |
| Soft deletion | No code path physically deletes an evidence item, case or audit record | Domain requirement DR-04 |

The final two standards were not present from the start. Single-source-of-truth was adopted as a rule *after* M1 demonstrated what its absence costs, and the soft-deletion rule was tightened after M2's finding D1. Recording the standards as they finished rather than as they began would misrepresent the project; the honest statement is that two of the seven are lessons rather than intentions.

## 10.2 The Data Layer

The data layer comprises six model classes mapped by SQLAlchemy onto six tables, whose schema is documented in Figure 8.3 and Appendix C.

**Table 10.3 — The six entities**

| Entity | Table | Purpose | Notable implementation feature |
|---|---|---|---|
| `Investigator` | `investigators` | Accounts, roles, keys, lockout state | Holds the Ed25519 public key and the Fernet-encrypted private key; exposes the three role predicates |
| `Case` | `cases` | Investigations | Soft archive via `is_archived`; generated `CASE-<year>-<nnn>` number |
| `EvidenceItem` | `evidence_items` | Registered digital exhibits | `original_hash` immutable, `current_hash` tracked separately; `integrity_status` written back by the verifier; `is_deleted` soft-delete flag |
| `CustodyLog` | `custody_logs` | Every custody event | `digital_signature` is `NOT NULL` — an unsigned record cannot exist |
| `AuditRecord` | `audit_records` | Append-only history | UPDATE and DELETE intercepted by ORM event listeners |
| `CaseAccess` | `case_access` | Case membership | Associative entity carrying permission level, grant time and grantor; source of `accessible_case_ids` |

Three implementation decisions in this layer are worth drawing out.

**Append-only enforced at the ORM layer.** SQLAlchemy event listeners on `AuditRecord` intercept any attempt to update or delete an audit record and raise. The guarantee is therefore a property of the data-access layer rather than something each route must remember to respect — it holds for code that has not been written yet. This is the Observer pattern of Table 9.8 doing the work that a convention could not.

**A lightweight startup migration.** Rather than adopting a full migration framework for a project of this size, the application inspects the existing columns at startup and adds any that are missing. This is what allowed M2's two new columns — `is_deleted` and `integrity_status` — to reach an existing database without a rebuild. Its limits are acknowledged: it adds columns but does not alter or drop them, which is sufficient for this project's history and would not be for a production system.

**One source of truth for time.** All timestamps are produced by a single local-time helper. This looks trivial and is not: M2's finding D6 was that one model's default bypassed the helper and produced a timezone-aware value while every other column was naive, creating a comparison hazard in exactly the two places that compare timestamps — the verifier's monotonicity check and the risk scorer's gap calculation.

## 10.3 Authentication, Authorisation and Session Management

### 10.3.1 Authentication

Authentication is implemented on Flask-Login. The login route verifies the submitted credentials against the stored salted hash and, on success, establishes a session, records a login event in the audit trail and — if the account has two-factor authentication enabled — diverts through a one-time-password verification step before completing the login.

The route **deliberately refuses to reveal whether a failed login was caused by an unknown email address or a wrong password**. This is a small design choice with a real consequence: the alternative allows an attacker to enumerate valid accounts by observing which error message is returned. It satisfies FR-01 and it is an instance of the exception-management threat category in Table 2.2.

Account security is hardened in three further ways. Repeated failed logins lock an account for a configured period, with an administrator able to unlock it, so that password guessing is throttled. The login route is rate-limited. Two-factor authentication uses TOTP through PyOTP with QR-code enrolment, so that when it is enabled a correct password is only the first factor. Together with the idle timeout below, these mean a stolen password alone does not grant lasting access.

### 10.3.2 Session Management

Sessions are governed by a **sliding idle timeout** implemented as a `before_request` hook: each request records its time, and if the gap since the previous activity exceeds the configured limit the user is logged out on the next request. Session cookies are set `HttpOnly` so that scripts cannot read them, `Secure` so that they travel only over TLS, and `SameSite=Lax` to resist cross-origin submission.

### 10.3.3 Authorisation

Authorisation is enforced at **two distinct granularities**, and keeping them distinct is the central idea of this subsystem.

**Table 10.4 — The two granularities of authorisation**

| Granularity | Question answered | Mechanism | Example |
|---|---|---|---|
| **Role** | What *kind of action* may this user perform? | Three predicates on `Investigator` — `is_admin`, `can_manage`, `can_analyse` — applied through route decorators | An Analyst may run an integrity check; a Read-Only auditor may not |
| **Case membership** | *Which data* may this user perform it on? | The `CaseAccess` table, via the `accessible_case_ids` helper | An Analyst may run an integrity check only on items in cases they belong to |

Because the four roles' capabilities strictly nest, the entire role policy is expressible in three predicates. Case membership is orthogonal to role and cannot be: it is a property of the user-case pair, not of the user.

The `accessible_case_ids` helper is the single most consequential function in the authorisation subsystem. It returns a sentinel meaning *all cases* for an administrator, the list of memberships for anyone else, and an empty list for a user belonging to no case. **Every aggregate query in the system routes through it.** The helper did not exist in the original implementation — the scoping rule was computed inline in the case list and nowhere else — and introducing it is what fixed M1 (Section 5.4.3). Its value is not that it fixed two defects but that it made the class of defect hard to reintroduce: the correct behaviour is now the obvious thing to call.

## 10.4 Case and Evidence Management

### 10.4.1 Cases

The case routes implement the full create-read-update-archive lifecycle. A new case receives a generated number of the form `CASE-<year>-<nnn>`, the sequence derived from the current case count; because deletion is soft the count never decreases, so the scheme remains collision-free in single-user operation. Its behaviour under concurrency is recorded as a known limitation rather than papered over.

The case list is scoped to the requesting investigator's memberships and paginated. Opening a case is guarded by a case-access check, and the case view lists the case's evidence items filtered to exclude soft-deleted ones. Archiving sets the status without removing data.

### 10.4.2 Evidence Registration

The evidence-upload route is where several requirements converge, and its ordering matters.

**Table 10.5 — The evidence upload sequence**

| Step | Action | Requirement |
|---|---|---|
| 1 | Check the file extension against the allow-list; reject if absent | FR-10 |
| 2 | Inspect the magic bytes and confirm the true MIME type matches the declared extension; reject executables outright | FR-14, FR-48 |
| 3 | Compute SHA-256 over the plaintext bytes; store as both `original_hash` and `current_hash` | FR-13 |
| 4 | Extract EXIF metadata via Pillow | FR-14 |
| 5 | Encrypt the file with AES-256-GCM and write it to the uploads area | FR-48 |
| 6 | Create the evidence record with a generated number, category, initial state, and the uploader as both creator and current holder | FR-11 |
| 7 | **In the same transaction**, create the initial `Upload` custody entry and sign it | FR-12, FR-23 |
| 8 | Write the audit record | FR-18 |

Step 7 is the invariant that makes the rest of the system safe: *every evidence item has a custody history from the moment it exists*. Because the record and its first custody entry are created in one transaction, there is no window in which an item exists without a chain — which is what allows the graph verifier of Section 11.2 to assume an upload root.

Step 3 occurring before step 5 is also deliberate: the hash is computed on the **plaintext**, so that integrity verification compares like with like after the verifier decrypts. Hashing the ciphertext would have made the stored hash depend on the encryption key and broken verification the moment the key changed.

Editing an item is permitted for title, description and category only; the file and its hashes are immutable through the editing path (FR-15).

## 10.5 The Custody Log and the Audit Trail

### 10.5.1 Custody Transfers

A transfer records the outgoing and incoming investigators, a timestamp, a location and a reason, and is permitted **only to the item's current holder or an administrator** — the rule that one cannot hand off what one does not hold. The custody log for an item is presented in chronological order, giving the human-readable chain of custody that the whole system exists to protect.

Every transfer is signed (Section 10.6). The route's error handling is **fail-visible**: if signing is unavailable, an explicit unsigned sentinel is recorded and the user warned, rather than the transfer aborting with a database error. This behaviour was standardised in M2 (finding D4) and is discussed as a design position in Section 11.2.1.

### 10.5.2 The Audit Trail

The audit trail is the system's memory. Every significant event writes a record carrying the event type, the acting investigator, the evidence and case concerned where applicable, the originating IP address, an outcome of Success, Failure or Warning, and a timestamp. The trail can be viewed per evidence item and per investigator by authorised users, and in full by administrators.

Two implementation properties matter. First, the append-only enforcement described in Section 10.2. Second, that the audit writes were **wired into each route as the route was written**, rather than retrofitted in a later pass — a decision the Increment 1 retrospective identifies as one of that increment's better ones, because it means the system was never in a state where its history was incomplete.

### 10.5.3 Formula-Based Audit Checks

The three formula checks are the clearest examples of Category A *formula* functionality: each is a direct computation over database fields rather than an algorithm.

**Table 10.6 — The three formula checks**

| Check | Computation | Why it matters forensically |
|---|---|---|
| **Custody time-gap** | Walk an item's custody entries in order; flag any interval between consecutive transfers exceeding a configurable threshold, default 72 hours | An unexplained gap in custody is exactly what undermines admissibility |
| **Duplicate entry** | Find custody records sharing event type, investigator pair and timestamp | Indicates accidental double-recording or deliberate log injection |
| **Role mismatch** | Compare the role of an investigator who accessed an item against the roles permitted for that item's category | Detects handling by someone whose role does not permit that evidence category |

These are exposed through a JSON endpoint for on-demand inspection, and — following M2's finding D5 — the duplicate and role-mismatch checks now feed **directly into the risk scorer**, so that two simple Category A computations become inputs to the complex Category C algorithm. This cross-category integration is discussed in Section 16.5.

## 10.6 Cryptographic Services

All cryptographic primitives come from established libraries; **no cryptography is implemented in this project**. What the project contributes is the protocol around them.

**Table 10.7 — Cryptographic services**

| Service | Primitive | Library | Application-side design |
|---|---|---|---|
| Content fingerprinting | SHA-256 | `hashlib` | Computed on plaintext at intake; `original_hash` never altered thereafter |
| Custody event signing | Ed25519 | `cryptography` | The **canonical payload** — the project's own design, described below |
| Evidence at rest | AES-256-GCM | `cryptography` | Authenticated encryption, so tampering with ciphertext is detectable, not merely undecryptable |
| Private keys at rest | Fernet | `cryptography` | Key derived from the application secret, so a database compromise alone yields no usable signing keys |
| Second factor | TOTP | PyOTP | Standard algorithm; works with any authenticator application |

### 10.6.1 The Canonical Signature Payload

Although Ed25519 is a library call, the **definition of what gets signed** is the project's own and is the single most rigour-demanding decision in the system (Table 3.3).

The payload signed for a custody event is a JSON serialisation, **with sorted keys**, of exactly six fields: the evidence identifier, the event type, the timestamp in ISO format, the outgoing and incoming investigator identifiers, and the file hash at the event. Sorting the keys makes the serialisation deterministic, so that the bytes produced when the record is created are byte-identical to the bytes reconstructed when it is later verified.

This is subtle and its violation is exactly the defect that independently-written signers and verifiers tend to exhibit. The Increment 1 retrospective carried an action to **fix this format before writing any signing code** (action A1-2), and the Increment 2 retrospective records that doing so is what made the eventual payload-mismatch bug tractable rather than mysterious — the mismatch was a timestamp-formatting difference, found in hours rather than days because there was a written definition to compare both implementations against.

The payload construction appears in three places — the custody route, the graph verifier, and the seed script — and all three produce identical bytes. That this is verifiable is the practical meaning of "formal" in Table 3.3.

## 10.7 Dashboards, Reporting and Export

### 10.7.1 Role-Tailored Dashboards

Following M1, each role sees a dashboard composed of panels matched to its work rather than a single shared view.

**Table 10.8 — Dashboard composition by role**

| Role | Panels |
|---|---|
| Administrator | System-wide totals; security alerts — locked accounts and recent failed logins |
| Lead Investigator | Pending actions — flagged items and items awaiting a lifecycle step, within their cases |
| Analyst | Workbench of the items they currently hold, with shortcuts to verify, transfer and change state |
| Read-Only Auditor | Review queue of recently updated items in their shared cases |
| *All roles* | "Your recent activity", drawn from the user's own audit records |

The "your recent activity" panel exists for a specific reason: it guarantees that **no dashboard is ever empty**. A user who belongs to no case sees an explanatory message directing them to request access, rather than a blank page or — as before M1 — a global view. This is the clearest instance in the project of a security constraint producing a better interface rather than a worse one.

### 10.7.2 Risk and Anomaly Views

The risk dashboard scores every accessible item, combines each item's deterministic and anomaly scores into a unified score weighted 0.6 to 0.4 in favour of the deterministic score, and ranks items highest-risk first. The per-item risk detail page gives the full factor breakdown, the interaction effects and the generated recommendations. The anomaly dashboard lists items by anomaly score with their feature vectors, framed as *suggested for review*.

The 0.6 / 0.4 weighting is a design position rather than a tuned parameter: the explainable, rule-based score is given the larger share deliberately, so that a statistical outlier detector trained on a small dataset informs prioritisation without overriding a score an investigator can actually reason about (domain requirement DR-07).

### 10.7.3 Tamper-Evident Export and PDF Report

The case export assembles a ZIP package containing the decrypted evidence files, a manifest recording each file's SHA-256, the full audit trail for the case, and an Ed25519 signature over the manifest together with the public key and instructions needed to verify it. A recipient can therefore confirm the package has not been altered since export **without access to the system that produced it** — which is what makes it court-ready rather than merely convenient.

The per-item PDF report, generated with ReportLab, produces a printable chain-of-custody document containing the item's identification, a cryptographic integrity summary that embeds a **fresh** run of the graph verifier, the full custody table and a generation footer. Running the verifier at generation time rather than reading a cached status is the same verifiability-over-performance choice made throughout: a printed document asserting integrity should assert the integrity of the item *now*, not when someone last happened to check.

## 10.8 The AI Assistant Interface

The assistant's orchestration logic is Chapter 11's subject; what belongs here is the interface and the engineering around the external call.

The chat interface posts the question to the assistant blueprint and renders the reply, with a metadata bar showing the classified intent, whether database context was used, and whether validation passed. Hallucination flags, when present, are displayed as an explicit warning attached to the answer rather than buried.

Three implementation details are worth recording because each was a defect repair.

**Untrusted output is escaped before rendering.** The model's reply is HTML-escaped first, and only then is the intended lightweight formatting re-applied. The original implementation rendered the reply as HTML directly, which — because a prompt-injection payload could be placed in a case title and steer the model — was a stored cross-site-scripting vector (M2 finding H1). The ordering matters: escape, then format, never the reverse.

**Conversation history is owner-tagged and cleared on both login and logout.** The original implementation stored history under a session key that logout did not clear, so on a shared browser one investigator's chat became visible to the next person to log in (M1, CR-02).

**The external call is bounded in time at three levels.** A per-model timeout of 20 seconds, a total budget of 60 seconds across all fallback candidates, and a browser-side abort at 90 seconds. The three are deliberately ordered so that the server always finishes and reports a real result rather than having the browser cancel a request that was still working — a failure mode the first attempt at this fix actually produced, because the per-model timeout exceeded the browser abort.

## 10.9 Summary

This chapter documented the construction of DEICMS subsystem by subsystem. The development environment and seven coding standards were recorded, with the honest note that two of the seven were adopted as lessons from maintenance rather than held from the start. The data layer's six entities were described, together with the three decisions that matter most: append-only enforced by ORM event listeners rather than by convention, a lightweight startup migration with stated limits, and a single source of truth for time whose one bypass became defect D6.

Authorisation was shown to operate at two orthogonal granularities — role for *what kind of action*, case membership for *which data* — with the `accessible_case_ids` helper identified as the subsystem's most consequential function. The eight-step evidence upload sequence was given with the requirement each step satisfies, and two orderings within it explained: the atomic creation of the first custody entry, and the hashing of plaintext before encryption. The custody log, the append-only audit trail and the three formula checks were described, including the cross-category integration that feeds two formula results into the risk scorer.

Cryptographic services were catalogued with a clear statement that no cryptography is implemented here, and the canonical signature payload — the project's own contribution — was specified along with the retrospective action that produced it. Dashboards, risk views, the tamper-evident export and the PDF report were described, and the AI assistant's interface was documented through the three defects that shaped it.

The next chapter treats the five complex algorithms algorithmically.
